# Functional Requirements

権限・データの意味・機能範囲の正本。画面の配置・色・動きは04_UI_UX_SPEC.mdと05_DESIGN_GUIDE.mdを正本とする。2026-09の目標仕様は11_DESIGN_REVISION.mdの対応Issueで段階適用し、現行実装と区別する。

## 1. ユーザー

role:

- `owner`
- `uploader`
- `viewer`

想定:

- 夫: owner
- 妻: owner
- 両親・兄弟など: viewer

### owner

- 投稿
- 閲覧
- コメント
- イベント作成・編集
- メンバー招待
- メンバー管理
- 全投稿編集・削除

ownerは他のメンバーのroleを変更・削除できる。削除したメンバーはログインできなくするが、過去の投稿・コメントなどの履歴は保持する。唯一のownerがいなくなる状態を避けるため、自分自身のrole変更・削除はできない。

### uploader

- 投稿
- 閲覧
- コメント
- イベント作成・編集・削除
- 全投稿編集・削除

### viewer

- 閲覧
- コメント

#### viewer向けUI

viewerには閲覧・コメントに不要な管理導線やメンバー情報を表示しない。

表示するもの:

- タイムライン
- イベント一覧・詳細
- 投稿詳細・Media Viewer
- コメント追加
- 自分のコメント削除
- 自分の表示名など最低限の個人設定

表示しないもの:

- 投稿追加タブ・投稿作成画面
- Event・見出しの作成・編集・削除
- 投稿の編集、投稿・Mediaの削除操作
- メンバー一覧・role・通知状態
- 招待・メンバー管理
- owner・uploader向け管理設定

非表示だけに依存せず、APIの認可とクライアントルーティングでもアクセスを拒否する。

## 2. データ階層

トップレベルの `Album` データ概念は作らない。アルバム画面は既存Mediaを年月ごとに表示するviewとして扱う。

アプリ全体が1つの「このごろ」。

```text
Event
  └─ 見出し (optional)
      └─ Post
          └─ Media
```

例:

```text
ドイツ新婚旅行
  └─ Day 2 - シュトゥットガルト
      ├─ ポルシェミュージアム
      │   └─ 写真18枚
      └─ 夜ごはん
          └─ 写真6枚
```

### Event

旅行や大きなお出かけ単位。

例:

- ドイツ新婚旅行
- 箱根温泉
- 佐原ドライブ
- 結婚記念日ディナー

Eventは任意。

### 見出し

Event内の整理単位。

内部データモデルとAPIでは`Scene`として扱うが、利用者向けの表記には「見出し」を使う。

例:

- Day 1 - フランクフルト
- Day 2 - シュトゥットガルト

見出しは任意。

見出しは1階層のみ。ネスト不可。

### Post

実際の投稿単位。

例:

- ポルシェミュージアム
- 夜ごはん
- ドイツ到着

Post titleは持たない。
Caption（画面上は「ひとこと」）は任意。

### Media

写真または動画。

複数Mediaを1Postにまとめる。

---

## 3. タイムライン

画面名は **「タイムライン」**。内部のTimelineデータ概念とURLは変更しない。

すべてのPostをイベント期間の新しい順に表示する。ホームではイベント開始日（開始日がない場合は終了日）を主キー、終了日、Event ID、Postの撮影日時、Post IDを順にタイブレークキーとする降順で、ページをまたいでも安定した順序にする。Eventに属さないPostは撮影日時、公開日時、作成日時の順で利用できる日付をイベント開始日・終了日の代わりに使う。

Eventに属さないPostも表示する。

Postカードには原則として以下を表示:

- 投稿者のプロフィールアイコン
- Event titleと見出し（存在する場合）
- Media Grid
- 「見た人」の人数とComment数
- Caption（存在する場合）
- 最新のComment 1件
- 残りのCommentを開く導線

写真1枚ごとをSNS投稿にしない。

投稿者名とプロフィールアイコンを表示し、Eventや見出しがない場合は「日常の投稿」などの代替分類を表示しない。コメント0件は「コメントを書く」、1件以上は「コメントN件」。最新1件と残りへの導線を維持する。詳細な配置は04_UI_UX_SPEC.mdの投稿カードに従う。

### お知らせ

画面名は「お知らせ」。互換性のためURLは`/activity`を維持する。公開投稿とコメントを時系列で表示し、対象投稿を開く。ownerのみメンバーの最終閲覧時間を表示でき、uploader・viewerへはAPIからも返さない。カーソルによる追加取得と失敗時の再試行を維持する。

---

## 4. 撮影日時

Mediaには撮影日時を保持する。

タイムラインの日付処理は原則としてアップロード日時ではなく撮影日時を利用する。

ただし投稿画面に「撮影日の扱い」などの説明UIは表示しない。

## 5. イベント

Eventには以下を持つ:

- id
- title
- description
- start_date
- end_date
- cover_media_id
- cover_object_key
- cover_source
- created_by
- created_at
- updated_at

`cover_source`:

- `auto`
- `manual`

### イベント一覧の状態と表示順

Eventの状態は保存せず、日本時間の当日とstart_date・end_dateから自動判定する。日付が片方だけの場合は、その日だけのEventとして扱う。

1. 進行中: 開始日から終了日まで。終了日が近い順
2. 予定: 開始日前。開始日が近い順
3. 日付未定: 日付が両方未設定。更新が新しい順
4. 終了: 終了日を過ぎたもの。終了日が新しい順

進行中と予定のEvent Cardには状態を表示する。予定Eventもメンバー全員へ表示し、事前に見出しやPostを準備できるようにする。

### カバー画像

原則自動選択。

1. 写真がある場合は写真から選択
2. 写真がなく動画のみなら動画の代表フレーム
3. ユーザーは手動変更可能
4. manualになった後は勝手に変更しない
5. 「自動選択に戻す」を用意する

動画の代表フレームは、Workerで重い動画処理をせず、ブラウザ側生成を優先する。

## 6. Event Detail

Event Detailは「そのEventだけに絞ったTimeline」。

上部:

- Cover
- Event title
- start/end date
- 写真数
- 動画数
- Post数

下部:

```text
見出し
  ↓
Post
  ↓
Media
```

見出しは一つの文字列として扱い、日と地名を別項目に分解しない。表示幅による自然な折り返しは許容する。

---

## 7. Post Detail

Timeline / Event Detail のどちらから入っても同じPost Detailを使う。

Post Detailは画面全体を覆うページとして表示する。Postを押したらデータ取得の完了を待たずにURLを切り替えて右からスライドインさせ、Skeleton、読み込み結果、読み込みエラーをページ内へ描画する。ページの表示とデータ取得は並行し、戻る操作では右へスライドアウトして遷移元とそのスクロール位置へ戻る。

ページ上部には共通タイトルを表示せず、戻るボタンと権限に応じた投稿メニューを配置する。読み込み中や読み込みエラーの状態でも戻れるようにする。

投稿情報はTimelineと同じ順序で表示し、Event titleにはカレンダーアイコン、見出しには装飾を付けない。CaptionとComment一覧は同じsurface上に置き、細い区切り線と余白で区別する。投稿内容とComment一覧だけをページ内でスクロールし、コメント投稿フォームはページ下端へ固定する。モバイルのsafe areaを確保し、キーボード表示中はフォームをキーボード直上に保つ。フォームによってComment一覧の末尾が隠れない余白を設ける。

表示:

- Event（存在する場合）
- 見出し（存在する場合）
- 撮影日
- 投稿者
- Media
- Caption
- Seen by
- Comments

右上の3点メニューから、権限があるユーザーだけが投稿を編集・削除できる。編集ではEvent、見出し、Captionに加えて、写真・動画の追加と削除ができる。写真・動画は合計30件までとし、投稿には1件以上残す。変更を保存するまでは既存Mediaを削除せず、追加Mediaのアップロードに失敗した場合は失敗した項目だけ再試行できる。投稿自体の削除前には写真・動画とコメントも削除され、元に戻せないことを確認するモーダルを表示する。

Event / 見出しがない場合、空ラベルを出さない。

## 9. 投稿作成

フロー:

1. 写真・動画を複数選択
2. Event選択
3. 見出し選択
4. ひとこと
5. 投稿

Event: optional
見出し: optional
Caption: optional

見出しはEvent選択時のみ利用可能。

投稿作成画面と投稿編集画面の両方から見出しを新規作成できる。見出しの追加後は、その見出しを選択した状態にする。投稿編集画面では写真・動画をドラッグ＆ドロップで並び替えられ、保存後もその順序を維持する。

見出しの管理はEvent Editへ集約する。

選択した写真はローカルのObject URLで即時表示し、動画は準備中であることが分かるプレースホルダーを即時表示する。端末内の準備処理は同時実行数を制限してUI操作とメモリを圧迫しないようにし、完了した項目からサムネイルへ切り替える。動画のサムネイルには先頭のデコード済みフレームを使い、動画同士を同時にデコードしない。準備中とアップロード中はヘッダー直下に固定した進捗を表示し、個別の準備失敗は対象項目から再試行できるようにする。投稿編集で写真・動画を追加する場合も同じ挙動とする。

## 11. 「見た人」

閲覧の自動既読を基本とする。明示的な既読専用ボタンは追加しない。

現行の判定:

- Post Cardの50%以上が画面内
- 2秒以上表示

既読は投稿が画面に表示された受信確認であり、全写真の閲覧・動画の完走を意味しない。#46で自動既読を維持しつつ、明示的な「次へ」でも記録できるようにする。判定領域、待機・失敗・件数の契約は04_UI_UX_SPEC.mdの新着閲覧フローに従う。

同一ユーザー・同一Postへ大量writeしないこと。

現在のユーザーがまだ見ていないPostは、TimelineとEvent DetailのPost Cardへ「未閲覧」と表示する。自動既読が記録されたら、その場で表示を消す。

viewerのタイムラインには未閲覧Postの合計件数と「新しい思い出を見る」導線を表示する。未閲覧が0件の場合は導線を表示しない。導線からは未閲覧Postを公開日時の古い順に1件ずつ閲覧し、現行は各Postの自動既読成功後に次へ進む。#46の目標は自動または明示操作による既読の成功後に次へ進む。最後のPostまで閲覧すると完了状態を表示する。途中離脱や別端末からの閲覧後は、サーバー上の`view_histories`を基準に残りの未閲覧Postから再開する。

UI:

```text
👀 3
```

元の目の絵文字を思わせる、可愛らしく横方向へ視線を向けたオリジナルの両目アイコンの右に見た人数を表示する。両目アイコンは塗りつぶさず、コメントアイコンと調和する輪郭線で表現する。タップするとボタンの上に「見た人」と閲覧者の一覧を表示し、各ユーザー名の左にプロフィール画像または頭文字アイコンを添える。数字やランキングを強調しない。お知らせ上部ではownerにのみ各メンバーの最終閲覧からの相対時間を「最後に見た時間」として表示する。

## 12. メンバー招待

ownerが招待URLを発行。

token:

- 7日間有効
- 原則1回利用
- D1にはtoken hashのみ保存

フロー:

```text
Invite URL
→ LINE Login
→ 「このごろ」からのLINE通知の受信確認
→ 参加確認
→ User登録
→ Timeline
```

LINE Login ChannelにはMessaging API Channelをリンクする。ログイン後に「このごろ」からの通知を受け取れる友だち状態を保存する。設定画面では「アプリからの通知」として受信状態を表示し、受信不可の場合だけLINEで「このごろ」アカウントをブロックしていないか確認するよう案内する。

ログインセッションは最終利用から約90日間有効とする。アプリ起動時の認証確認で期限を更新し、利用中のAPIリクエストごとには更新しない。90日間利用しなかった場合、明示的にログアウトした場合、またはメンバーが無効化された場合は再ログインを求める。

Messaging APIのWebhookで友だち状態を同期する。`unfollow`受信時は友だち状態とLINE通知をOFFにし、`follow`受信時は友だち状態だけをONにする。ブロック解除によってLINE通知を自動で再開せず、ユーザーが設定画面で改めてONにする。

Webhookは受信したraw bodyとMessaging API Channel Secretを用いて`x-line-signature`を検証してから処理する。署名がない、または不正なリクエストでは状態を更新しない。複数eventと再送を安全に処理し、対象メンバーが存在しないeventは正常応答として無視する。LINE Developers Consoleによる疎通確認の空eventにも正常応答する。

## 13. LINE通知

「このごろ」のLINEアカウントから通知する。

Mediaごと / Postごとの即時通知はしない。

短時間の投稿をまとめる。

例:

```text
22:00 写真10枚
22:03 写真5枚
22:06 動画2本
↓
約10分後
写真15枚・動画2本が追加されました
```

Cloudflare Cron Triggersで通知batchを処理。

通知本文のURLはbatch内で最も新しく公開された投稿を直接開く。通知に写真や動画のサムネイルは載せない。ログインが必要な場合も、LINE Login完了後に同じ投稿へ戻す。

ユーザーごとに通知ON/OFFを持つ。「このごろ」のLINEアカウントを友だち追加済みかつブロックしていないユーザーだけを送信対象にする。友だち状態はLINE Login後の確認に加え、Messaging APIの`follow`・`unfollow`Webhookで更新する。

## 15. エラー

考慮するもの:

- D1 error
- R2 upload error
- Presigned URL取得失敗
- upload途中失敗
- complete API失敗
- unsupported file
- file size error

複数uploadでは1件失敗で全体を失敗扱いにしない。

成功済みMediaは維持。
失敗Mediaのみ再試行可能にする。

## 16. 読み込み状態

データ取得中の各画面には、完成後のレイアウトに近いSkeletonを表示する。画像、見出し、本文などの領域をあらかじめ確保し、読み込み完了時のLayout Shiftを抑える。

Skeletonの個々の装飾は読み上げ対象にせず、読み込み領域へ`aria-busy="true"`を付け、支援技術には読み込み中であることを伝える。`prefers-reduced-motion: reduce`ではshimmer animationを停止する。
