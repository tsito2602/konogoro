# 思い出の検索・整理に関する判断

Issue #9で、高度な検索を先行実装せずに済むかを判断した記録。2026年9月時点のプロダクト構成を対象とする。

## 結論

現時点では横断検索を追加しない。主な利用者は1家族内の少人数で、次の既存導線が代表的な探し方をすでに分担している。

| 探したい場面 | 現在の導線 | 対応できる範囲 |
| --- | --- | --- |
| 最近追加された写真を見る | ホームの未閲覧件数と新着閲覧フロー | 未閲覧投稿を古い順にすべて確認 |
| 撮影時期から探す | ホームの年月見出し、アルバムの年・月選択 | 投稿日ではなく撮影日時を基準に移動 |
| 旅行・外出から探す | イベント一覧・詳細 | タイトル、メモ、期間、状態で絞り込み |
| 写真を一覧して探す | アルバム | 年全体または月ごとのグリッド表示 |
| 誰が追加したか確認する | 投稿カードの投稿者表示 | 見つけた投稿上で確認可能 |

投稿者による絞り込みだけは専用導線がないが、夫婦を中心とする少人数利用では選択肢の追加コストに対する効果が小さい。全文検索、タグ、顔認識、外部検索サービスはプロダクトの静かで単純な閲覧体験に対して過剰になる。

## データ量の確認方法

個人情報を含む本文やファイル名を取得せず、件数と期間だけをD1で確認する。

```sql
SELECT
  COUNT(*) AS published_posts,
  MIN(COALESCE(captured_at, published_at)) AS oldest_post_at,
  MAX(COALESCE(captured_at, published_at)) AS newest_post_at
FROM posts
WHERE status = 'published';

SELECT COUNT(*) AS events FROM events;

SELECT
  COUNT(*) AS uploaded_media,
  SUM(CASE WHEN kind = 'image' THEN 1 ELSE 0 END) AS images,
  SUM(CASE WHEN kind = 'video' THEN 1 ELSE 0 END) AS videos
FROM media
WHERE status = 'uploaded';
```

本番データをstagingへ複製せず、集計値だけを運用確認に使う。現在は初期運用段階で、既存APIの取得単位はホーム20投稿、アルバム60メディア、お知らせ40件であり、いずれもcursor paginationにより全期間へ移動できる。将来は月100投稿・500メディアが2年間続く約2,400投稿・12,000メディアを、検索を再検討する目安として想定する。

## 再検討条件

次のいずれかを満たした場合に、実際に困った探し方を添えて独立Issueを作成する。

- 公開済み投稿が2,000件、またはアップロード済みメディアが10,000件を超える
- 利用期間が2年を超え、既存の年・月・イベント導線で目的の投稿を見つけられない事例が月2回以上ある
- 5人以上の利用確認で、2人以上が同じ検索軸（日付、イベント、投稿者）を必要とする
- 1家族内の投稿者が5人以上になり、投稿者から探す要望が継続する

## 再検討時の最小構成

最初に追加する候補は、ホーム上部の絞り込みから「撮影期間」「イベント」「投稿者」を組み合わせるサーバー側filterとする。結果0件、cursor pagination、日付境界、role別の閲覧権限、モバイル操作を検証する。全文検索、AI分類、顔認識、タグ体系はこの最小構成に含めない。
