# 動画中心の閲覧・R2性能改善

対象: #56（仕様）、#57（配信）、#58（再生用動画）、#59（分割送信）、#60（鑑賞）、#61（一覧API）。先行UI改善PR #55に依存する。メディア契約と送信・再生・一覧が相互依存するため一つの統合PRで検証する。

## 採用する構成

R2はprivateのまま。元ファイルは保存用、PCで作った軽量MP4は閲覧用、WebP画像は一覧用に分ける。既存投稿に再生用動画がない場合は元動画を再生する。Stream、追加クラウド、独自ドメイン契約は必要としない。

再生用動画の作成は任意のPC操作。毎回の通常投稿に変換を強制しない。これは既存動画すべての自動最適化ではない。元ファイルの保存時間は容量と利用回線にも左右され、再生開始の改善とは別に測る。

CDNは今回は追加しない。現在のS3署名URLとworkers.devのまま設定だけ足しても期待する共有キャッシュにならないため、まず転送量、正しいvariant配信、必要な分の先読みを改善する。将来導入する場合は独自ドメイン・認証・キャッシュ失効を一体で設計する。

## 一覧APIの測定

`src/worker/list-summary.test.ts` は実SQLiteと実API handlerで合成データを検証する。1投稿に公開メディア30件（写真29・動画1）、コメント80件（約200文字ずつ）、未確定メディア1件を作り、同じ投稿のsummary/detailを比較する。

| 比較 | JSONのUTF-8サイズ | メディア配列 | コメント配列 |
| --- | ---: | ---: | ---: |
| 従来相当の詳細取得 | 40,444 bytes | 30件 | 80件 |
| 一覧用取得 | 2,327 bytes | 4件（代表動画を含む） | 最新1件 |

この合成条件では約94%削減。圧縮前JSONの比較であり、本番通信の速度や全投稿で同率の改善を保証する数値ではない。メディア30件・コメント80件という総件数、投稿順、既読、詳細での全件表示は維持する。

## 計測と確認方法

- API: `Server-Timing: app;dur=...` は認証を含むhandler処理の実測。R2動画全体の転送完了時間は含まない。
- 動画: 再生操作から最初のplayingまで、bufferingの回数と待機時間を端末内で計測する。署名URL・メディア本文・氏名・コメントは外部へ送信しない。
- 同一サンプルで初回と再訪を分け、同じ端末・同じ回線で比較する。先読み有無、元動画/再生用動画、縦/横、動画のみ/混在を記録する。
- 先読みは次1本に制限する。8MiB以内の再生用動画だけを対象に、3秒以内・受信量上限で打ち切る。先読みしたBlobを実際の再生へ引き継ぐ。大きな動画や元動画へ自動先読みを拡張しない。
- DLはHEAD/Content-Length、Rangeの206/416、If-Range、ETag、認証、ストリームを検証する。ブラウザのDL再開機能や回線を保証しない。
- multipartは部分失敗、再試行、URL再発行、完了応答喪失、中止、投稿権限を検証する。ブラウザ終了後のFile復元は含まない。
